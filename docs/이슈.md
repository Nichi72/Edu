## #1 · Active Input Handling 이 syllabus와 어긋나 있다 — **높음**

**발견 시점**: Phase 0 착수 전 사전 조사

```
ProjectSettings/ProjectSettings.asset
  activeInputHandler: 1        ← Input System Package (New) 전용
```

**문제**
- `syllabus.md` cp-00 체크는 **`Both`** 를 요구한다
- cp-08 개념은 `Input.GetKeyDown(KeyCode.Space)` — **구 Input Manager API** 다
- New 전용 상태에서 이 API를 호출하면 런타임에 `InvalidOperationException` 이 난다
  (`You are trying to read Input using the UnityEngine.Input class, but you have switched active Input handling to Input System package in Player Settings.`)

**영향 범위**
이 프로젝트만의 문제가 아니다. Unity 6 URP 3D 템플릿의 **기본값이 New 전용**이므로, 학생이 cp-00에서 `Both` 로 바꾸는 걸 놓치면 **8번 항목까지 진도를 나간 뒤에야 터진다.** 그 시점엔 원인이 코드에 있다고 착각하기 쉽다.

**대응**
- 레퍼런스: Phase 0에서 `Both` 로 변경
- 교재: cp-00 시연 절차에 **"Active Input Handling 을 Both 로 바꾼다"를 눈에 띄게 넣는다.** 안 바꿨을 때 나오는 에러 메시지 전문을 cp-08 "흔한 막힘"에 실어둔다

## ~~#4~~ · 카메라 Orthographic Size 가 어디에도 없는데, 체크 4개가 이 값에 의존한다 — **해소됨 (cp-02)**

**발견 시점**: 착수 전 syllabus 정합성 대조

cp-02 개념에 `Orthographic 카메라` 가 있고 체크는 `Aspect 가 16:9` 까지만 요구한다.
**그런데 Orthographic Size 값이 syllabus 어디에도 적혀 있지 않다.** 이 값이 화면에 보이는 범위를 결정하므로, 아래 체크가 전부 여기에 매인다.

| 체크 | 어떻게 의존하나 |
|---|---|
| cp-06 `3초 안에 화면 아래로 사라진다` | 화면 아래 끝이 y 몇인지에 따라 달라진다 |
| cp-09 `천장 y=4.5 / 바닥 y=−3.5` | 이 값이 화면 안이어야 말이 된다 |
| cp-10 `x=11 출발, 약 7~8초 뒤 화면 밖` | 화면 왼쪽 끝이 x 몇인지에 따라 달라진다 |
| cp-15 `미리 깔린 파이프 2개가 화면 안에 보인다` | 화면 가로 폭이 파이프 간격 6보다 넓어야 2개가 보인다 |

**Size = 5 로 확정하면 전부 맞아떨어진다.**

- 세로: y = −5 ~ 5. cp-09 의 천장 4.5 / 바닥 −3.5 가 화면 안에 들어온다 ✓
- 가로: 16:9 이므로 half-width = 5 × 16/9 ≈ **8.89**. x = −8.89 ~ 8.89
- cp-10: x=11 에서 출발해 완전히 사라지려면 약 x=−9.4 까지. 속도 3 이면 20.4/3 ≈ **6.8초**
  → 체크의 "약 7~8초" 와 살짝 어긋난다. **속도를 3 그대로 두면 6.8초, 2.7 로 낮추면 7.6초.**
  실측해서 어느 쪽이 맞는지 확정해야 한다
- cp-15: 화면 가로 17.8 > 파이프 간격 6 → 2개가 넉넉히 보인다 ✓

**대응**
- 레퍼런스: cp-02 에서 Size = 5 로 고정하고, cp-10 소요 시간을 실측한다
- 교재: **cp-02 시연 절차에 Size 값을 명시한다.** 지금 상태로는 학생마다 다른 값이 되고, 그러면 cp-06·09·10 체크가 사람마다 다르게 나온다
- 실측 후 cp-10 의 "7~8초" 가 안 맞으면 syllabus 숫자를 고쳐야 한다

## #5 · cp-06 의 "3초 안에" 는 PC 성능에 따라 달라진다 — **중간**

cp-06 은 `Time.deltaTime` 이 아직 없다(07에서 열린다). 그래서 낙하가 **프레임당 고정값**이고, 체크의 `Play 후 3초 안에 화면 아래로 사라진다` 가 **프레임레이트에 매인다.**

- 60fps 에서 3초 안에 떨어지도록 값을 잡으면 → 30fps 인 PC 에서는 6초가 걸려 **체크 실패**
- 144Hz 모니터에서는 1.25초 만에 사라진다

이건 버그가 아니라 **cp-07 이 가르치려는 바로 그 현상**이다. 다만 cp-06 단계에서 체크가 실패하면 학생은 자기 코드가 틀린 줄 안다.

**대응**
- 레퍼런스: 낙하값을 60fps 기준으로 잡고 실제 소요 시간을 기록한다
- 교재: cp-06 "흔한 막힘" 에 **"3초는 60fps 기준이다. 느린 PC 면 더 걸리는 게 정상이고, 그 이유는 07에서 밝혀진다"** 를 넣는다. 튜터가 먼저 이유를 말하면 07의 학습이 사라지므로, **현상만 인정하고 이유는 미룬다**

## #4 해소 기록 — cp-02 에서 실측

**결론: syllabus 가 틀린 게 아니라 값이 안 적혀 있었을 뿐이다. Size = 5 를 명시하는 것으로 끝.**

### 실측값 (Ortho Size 5, Aspect 16:9 / 1920x1080)

```
화면 세로   y = -5.000 ~  5.000
화면 가로   x = -8.889 ~  8.889     (Viewport→World 변환으로 교차검증, 일치)
바닥 윗면   y = -4.000              (Renderer.bounds.max.y)
새가 바닥에 얹힐 때 중심 y = -3.50   ← cp-09 의 "바닥 -3.5"
새가 천장에 닿을 때 중심 y =  4.50   ← cp-09 의 "천장 4.5"
```

**cp-09 의 4.5 / -3.5 는 임의로 고른 숫자가 아니라 Size 5 + 새 스케일 1 에서 기하학적으로
유도되는 값이었다.** 설계된 숫자였고, 다만 그 전제(Size)가 문서에 없었다.

### 대안값 측정 — Size 5 만 성립한다

| Size | 화면 세로 | 천장 닿을 때 | 바닥이 보이나 | cp-09 일치 |
|---|---|---|---|---|
| 3 | ±3.00 | 2.50 | ✗ 화면 밖 | ✗ |
| 4 | ±4.00 | 3.50 | ✗ 화면 밖 | ✗ |
| **5** | **±5.00** | **4.50** | O | **O** |
| 6 | ±6.00 | 5.50 | O | ✗ |
| 5 (재측정) | ±5.00 | 4.50 | O | O |

### 수정 기준 통과 여부

| 기준 | 결과 |
|---|---|
| ① 실측했다 | O — Roslyn 으로 카메라·Renderer bounds 측정, Viewport 변환 교차검증 |
| ② 2회 이상 재현 | O — Size 5 를 두 번 측정, 동일 |
| ③ 대안을 재봤다 | O — 3/4/6 전부 측정. 왜 안 되는지 확인 |
| ④ 의도가 아니다 | O — 값 누락은 학습 장치가 아니다. 명시하지 않으면 학생마다 화면이 달라져 cp-09 체크가 사람마다 다르게 나온다 |

### 조치

`syllabus.md` cp-02 체크에 추가:
> **카메라는 Position (0, 0, −10) 에 Orthographic `Size` = 5 다**(이 값이라야 09 의 천장 4.5 / 바닥 −3.5 가 화면과 맞는다)

## #6 · 카메라 기본 Y 가 1 이라 바닥이 안 보인다 — **교재에 반영함**

**발견 시점**: cp-02 제작 중

Unity 가 URP 프로젝트를 만들 때 `Main Camera` 의 `Position Y` 를 **1** 로 넣는다.
그대로 두면 화면 세로가 `-4 ~ 6` 이 되는데, **바닥 윗면이 정확히 -4 라서 한 픽셀도 안 보인다.**

지운 것도 아닌데 사라진 것처럼 보여서 초보가 오래 헤맨다. 실제 화면을 찍어
`docs/shots/cp-02/pitfall-camera-y1.png` 에 남겼다.

**syllabus 수정은 하지 않았다.** cp-02 체크에 카메라 Position 을 명시한 것으로 충분하고,
이 실패는 **학생이 직접 겪는 게 낫다** — 좌표로 화면을 추론하는 첫 경험이 되기 때문이다.
교재의 「안 되면」 절과 교수 메모의 「먼저 겪게 할 것」 에 반영했다.

## #7 · 튜터 규칙의 설명 게이트 목록이 syllabus 와 안 맞는다 — **높음 / 고침**

**발견 시점**: cp-03 착수 중, 이 항목이 게이트인지 확인하다가

`CLAUDE_Test_.md` 는 게이트 항목을 이렇게 정의한다.

> `체크` 문장이 "자기 말로 설명한다 / 말한다"로 끝나는 항목 — **cp-02, cp-03, cp-05, cp-09, cp-18, cp-26**

**기준은 맞는데 열거된 목록이 틀렸다.** syllabus 를 실제로 대조한 결과:

| | 목록 |
|---|---|
| 실제로 설명을 요구하는 항목 | cp-02, **04**, 05, **07**, **10**, **12**, 18 |
| CLAUDE_Test_.md 가 지목한 것 | cp-02, ~~03~~, 05, ~~09~~, 18, ~~26~~ |

### 근거 — 각 항목 체크 문장의 끝

```
cp-03  "...Game 뷰에서 한눈에 구분된다"                        → 설명 요구 없음
cp-04  "...그 차이를 자기 말로 설명한다"                       → 요구함 (누락돼 있었다)
cp-07  "...deltaTime 을 곱하는 이유를 자기 말로 설명한다"       → 요구함 (누락돼 있었다)
cp-09  "...Dead 로그가 딱 한 번만 찍힌다"                      → 설명 요구 없음
cp-10  "...새 코드와 뭐가 같고 뭐가 다른지 말한다"              → 요구함 (누락돼 있었다)
cp-12  "...'간격 × 속도 = 파이프 사이 거리' 를 자기 말로 설명한다" → 요구함 (누락돼 있었다)
cp-26  "...Unity 없이 실행해 5점 이상을 낸다"                   → 설명 요구 없음
```

### 왜 중요한가

누락된 넷이 **하필 수업에서 가장 중요한 개념**이다.

- **cp-04** — `Start` 는 한 번, `Update` 는 매 프레임. 이걸 모르면 05 부터 전부 막힌다
- **cp-07** — `deltaTime` 을 곱하는 이유. 이 수업에서 가장 어려운 개념이다
- **cp-10** — 새 코드와 파이프 코드가 뭐가 같고 다른지. **"응용"을 스스로 알아채는 순간**이라
  syllabus 가 일부러 체크로 박아둔 것이다
- **cp-12** — 간격 × 속도 = 거리. 15 의 미리 깔기 계산이 여기 기댄다

반대로 게이트가 잘못 걸려 있던 cp-03(색 고르기)·cp-09·cp-26(빌드)은 설명할 개념이 없어서,
튜터가 억지 질문을 만들어내게 된다.

### 조치

`CLAUDE_Test_.md` 의 목록을 **cp-02, cp-04, cp-05, cp-07, cp-10, cp-12, cp-18** 로 고쳤다.
"여섯 개" 라고 적힌 두 군데도 "일곱 개" 로 맞췄다.

**syllabus 는 안 고쳤다.** 틀린 쪽은 튜터 규칙이지 syllabus 가 아니다.
