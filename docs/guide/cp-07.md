> **이번 목표** — 두 가지를 고친다.
> ① 낙하 속도를 **코드를 열지 않고** Inspector 에서 바꾼다
> ② **어느 PC 에서나 같은 속도로** 떨어지게 만든다

06번에서 남긴 두 가지 불편을 여기서 해결한다. **이 수업에서 가장 어려운 개념이 나온다.** 천천히 가자.

## 시작하기 전에

- [ ] Play 하면 새가 계속 아래로 내려가 화면 밖으로 사라진다
- [ ] 속도를 바꾸려면 **코드를 열어야** 한다 ← 불편한 점 ①
- [ ] PC 마다 떨어지는 속도가 다르다 ← 불편한 점 ②

## 알아야 할 것

### `public` 과 `private`

**"이 상자를 밖에서 볼 수 있게 할까?"** 를 정하는 말이다.

| | 뜻 | Inspector 에 |
|---|---|---|
| `public` | 밖에서 볼 수도, 고칠 수도 있다 | **보인다** |
| `private` | 이 스크립트 안에서만 쓴다 | 안 보인다 |

**아무것도 안 쓰면 `private` 이다.** 지금까지 쓴 변수들이 Inspector 에 안 보였던 이유다.

### 변수를 메서드 밖으로 빼기

지금까지는 변수를 `Update()` **안**에 썼다.

```csharp
void Update()
{
    float fallSpeed = 0.05f;    // Update 안 → 매 프레임 새로 만들어지고 사라진다
    ...
}
```

이러면 Inspector 에 노출할 수 없다. **밖으로 빼야 한다.**

```csharp
public class BirdMove : MonoBehaviour
{
    public float fallSpeed = 3f;    // 클래스 안, 메서드 밖 → Inspector 에 보인다

    void Update()
    {
        ...
    }
}
```

⚠️ **위치가 중요하다.** `class` 의 중괄호 **안**이면서, `void Update()` 의 중괄호 **밖**이어야 한다.

### Inspector 노출

`public` 변수는 **Inspector 에 칸이 생긴다.**

- Unity 가 이름을 알아서 예쁘게 바꿔준다: `fallSpeed` → **`Fall Speed`**
- **Play 중에도 실시간으로 바꿀 수 있다.** 값을 바꾸면 즉시 반영된다

⚠️ **아주 중요 — Inspector 값이 코드보다 세다.**

```csharp
public float fallSpeed = 3f;    // 이건 "처음 만들 때의 기본값" 일 뿐이다
```

한 번 Inspector 에 칸이 생기면 **Unity 는 씬에 저장된 값을 쓴다.** 코드의 `3f` 를 `10f` 로 고쳐도 Inspector 값은 안 바뀐다. 이걸 모르면 "코드를 고쳤는데 왜 그대로지?" 로 한참 헤맨다.

**값은 Inspector 에서 바꾸자.** 그게 이 항목의 목적이다.

### 프레임레이트 (FPS)

**1초에 화면을 몇 장 그리는지**다. `frames per second` 를 줄여 fps 라고 한다.

- 좋은 PC: 1초에 60장, 120장, 144장…
- 느린 PC: 1초에 30장, 20장…

**PC 마다 다르다.** 그리고 같은 PC 라도 상황에 따라 달라진다.

### `Time.deltaTime` ★

**직전 프레임에서 지금 프레임까지 걸린 시간(초)** 이다.

| 1초에 그리는 장수 | 한 장에 걸리는 시간 = `Time.deltaTime` |
|---|---|
| 60장 | 1 ÷ 60 = 약 **0.017초** |
| 30장 | 1 ÷ 30 = 약 **0.033초** |
| 10장 | 1 ÷ 10 = 약 **0.1초** |

**빠른 PC 는 작고, 느린 PC 는 크다.** 정확히 반대로 움직인다.

### 왜 곱하면 같아지나 ★★

이게 이번 항목의 핵심이다.

**06번 방식 — 프레임당 얼마씩**

```csharp
transform.position += new Vector3(0f, -0.05f, 0f);
```

"한 프레임에 0.05칸" 이다. 그러면 1초에 가는 거리는

```
60장 PC : 0.05 × 60장 = 1초에 3칸
30장 PC : 0.05 × 30장 = 1초에 1.5칸     ← 절반밖에 못 간다
```

> **비유** — "한 걸음에 5cm 씩 간다" 고 정하면, **걸음이 빠른 사람이 더 멀리 간다.**

**07번 방식 — 초당 얼마씩**

```csharp
transform.position += new Vector3(0f, -fallSpeed * Time.deltaTime, 0f);
```

`fallSpeed` 를 **"1초에 갈 거리"** 로 정하고, 여기에 **이번 프레임이 걸린 시간**을 곱한다.

```
60장 PC : 3칸/초 × 0.017초 = 한 프레임에 0.05칸  → 1초에 3칸
30장 PC : 3칸/초 × 0.033초 = 한 프레임에 0.1칸   → 1초에 3칸    ← 같다!
```

**프레임이 짧으면 조금 가고, 길면 많이 간다.** 그래서 1초에 간 거리는 언제나 같다.

> **비유** — "1초에 3m 씩 간다" 로 정하면, **걸음이 빠르든 느리든 1초 뒤엔 같은 자리**다.

⚠️ **곱하기를 빼먹으면 06번으로 돌아간다.** 앞으로 **움직임을 다루는 곳마다 `Time.deltaTime` 을 곱한다.** 13번의 시간 재기에서도 다시 쓴다.

### 단위가 바뀐다

**같은 이름의 변수인데 뜻이 달라진다.**

| | `fallSpeed` 의 뜻 | 값 |
|---|---|---|
| 06번 | **한 프레임에** 갈 칸 수 | 0.05 |
| 07번 | **1초에** 갈 칸 수 | 3 |

`0.05 × 60 = 3` 이라서, 60fps PC 에서는 결과가 똑같다. **값이 60배 커진 게 아니라 단위가 바뀐 것이다.**

## 해보기

### 1. 순서부터 세운다

이번엔 고칠 곳이 **세 군데**다. 무엇을 고쳐야 할지 적어보자.

```
1. ________________________________
2. ________________________________
3. ________________________________
```

> 막히면 이 셋을 답해보자.
> - Inspector 에 보이게 하려면 변수를 **어디에** 두고 **무슨 말**을 붙여야 하나?
> - "한 프레임에 0.05칸" 을 "1초에 3칸" 으로 바꾸면 값이 얼마가 되나?
> - 프레임마다 실제로 움직일 거리를 구하려면 무엇을 **곱해야** 하나?

### 2. 코드 고치기

```csharp
using UnityEngine;

public class BirdMove : MonoBehaviour
{
    ________ float fallSpeed = ________;

    void Update()
    {
        transform.position += new Vector3(0f, -fallSpeed * ________________, 0f);
    }
}
```

**빈칸 힌트**

| 빈칸 | 힌트 |
|---|---|
| `float` 앞 | Inspector 에 보이게 하는 말 |
| `fallSpeed` 값 | **1초에** 몇 칸 갈 것인가. 06번과 같은 느낌을 내려면 `0.05 × 60` |
| `-fallSpeed *` 뒤 | 이번 프레임이 걸린 시간. `Time.` 으로 시작한다 |

> 변수가 `Update()` **밖**, `class` **안**에 있어야 한다. 위치를 꼭 확인하자.

### 3. Inspector 확인

1. `Ctrl + S` 로 저장하고 Unity 로 돌아온다
2. **Hierarchy** 에서 `Bird` 를 클릭한다
3. **Inspector** 의 `Bird Move (Script)` 칸을 본다

**`Fall Speed` 라는 칸에 `3` 이 들어 있으면 성공이다.**

### 4. 코드를 열지 않고 속도 바꾸기

1. **Play** 를 누른다
2. Play 중에 Inspector 의 `Fall Speed` 를 **`1`** 로 바꿔본다 → 느려진다
3. **`10`** 으로 바꿔본다 → 빨라진다
4. **Stop**

> Play 중에 바꾼 값은 Stop 하면 사라진다 (05번에서 배운 것). **남기려면 Stop 상태에서 바꾸자.**
> 실험이 끝나면 `3` 으로 되돌려두자.

### 5. 실험 — 어느 PC 에서나 같은지 확인하기

**이게 이번 항목의 진짜 확인이다.** PC 를 바꿀 수는 없으니, **일부러 느리게 만들어서** 비교한다.

`BirdMove.cs` 에 **임시로** 두 가지를 넣는다.

```csharp
using UnityEngine;

public class BirdMove : MonoBehaviour
{
    public float fallSpeed = 3f;

    void Start()
    {
        Application.targetFrameRate = 60;    // ← 실험용. 나중에 지운다
    }

    void Update()
    {
        transform.position += new Vector3(0f, -fallSpeed * Time.deltaTime, 0f);

        Debug.Log(Time.time + "초   y = " + transform.position.y);   // ← 실험용. 나중에 지운다
    }
}
```

> `Time.time` 은 **Play 를 누른 뒤 흐른 시간**이다.
> `+` 로 글자와 숫자를 이어붙이면 한 줄로 찍힌다.

**실험 절차**

1. Console 의 `Collapse` 를 **끈다**, `Clear` 를 누른다
2. `targetFrameRate = 60` 인 상태로 **Play** → 새가 사라지면 **Stop**
3. Console 을 위에서 아래로 훑어, **`y` 가 처음으로 −5.5 보다 작아진 줄**을 찾아 **시간을 적는다**
4. 코드의 `60` 을 **`10`** 으로 바꾸고 저장
5. Console `Clear` → **Play** → **Stop** → 같은 방법으로 시간을 적는다
6. **두 시간을 뺀다**

이 교재를 만들면서 실제로 재본 값이다.

| `targetFrameRate` | 그려진 프레임 수 | 한 프레임당 시간 | **사라진 시각** |
|---|---|---|---|
| 60 | 77장 | 0.024초 | **1.840초** |
| 10 | 17장 | 0.113초 | **1.926초** |

**차이는 0.086초.** 프레임 수는 **4.5배** 차이인데 시간은 거의 같다.

**06번 방식이었다면 이랬다.**

| | 빠를 때 | 느릴 때 | 차이 |
|---|---|---|---|
| 06번 (곱하기 없음) | 1.98초 | 3.64초 | **1.65초** |
| 07번 (`deltaTime` 곱함) | 1.84초 | 1.93초 | **0.09초** |

### 6. 실험용 코드 지우기

확인이 끝나면 `Start()` 덩어리와 `Debug.Log` 줄을 **지운다.**

### 말로 설명해보기 ★

> **왜 `Time.deltaTime` 을 곱할까? 곱하지 않으면 무슨 일이 생길까? 자기 말로 설명해보자.**

이걸 설명할 수 있으면 통과다. **못 하면 넘어가지 말자.** 앞으로 움직임이 나올 때마다 이 곱하기가 나온다.

## 안 되면

### Inspector 에 `Fall Speed` 칸이 안 보인다

**원인 1** — `public` 을 안 붙였다.

**원인 2** — 변수가 `Update()` **안**에 있다. `class` 안이면서 메서드 밖으로 빼자.

```csharp
public class BirdMove : MonoBehaviour
{
    public float fallSpeed = 3f;    // ← 여기 (메서드 밖)

    void Update()
    {
        // ← 여기 아님 (메서드 안)
    }
}
```

**원인 3** — 컴파일 에러가 있다. Console 의 빨간 줄부터 없애자.

### 코드의 숫자를 고쳤는데 안 바뀐다

**원인** — **Inspector 값이 코드보다 세다.**

```csharp
public float fallSpeed = 3f;
```

이 `3f` 는 **"처음 만들 때의 기본값"** 일 뿐이다. 한 번 칸이 생기고 나면 Unity 는 씬에 저장된 값을 쓴다.

**고치는 법** — 값은 **Inspector 에서** 바꾸자. 그게 이 항목의 목적이다.

> 굳이 코드 기본값을 다시 적용하고 싶으면, Inspector 의 `Bird Move (Script)` 오른쪽 점 세 개(⋮) → `Reset`.

### 새가 너무 빨리 떨어진다

**원인** — 값을 그대로 `0.05` 로 뒀다면 반대다. **너무 느릴** 것이다.

06번의 `0.05` 는 **한 프레임에** 갈 거리였고, 07번의 값은 **1초에** 갈 거리다. **단위가 바뀌었다.**
06번과 같은 느낌을 내려면 `0.05 × 60 = 3` 이다.

### `targetFrameRate` 를 바꿔도 안 느려진다

**원인** — **vSync 가 켜져 있으면 `targetFrameRate` 가 무시된다.**

vSync 는 모니터 주사율에 맞춰 그리는 기능이다. 켜져 있으면 프레임 수를 우리가 못 정한다.

**고치는 법** — `Edit > Project Settings > Quality` 에서 `V Sync Count` 를 `Don't Sync` 로.

> 이 교재의 프로젝트는 처음부터 꺼져 있어서 손댈 필요가 없었다.

### 새가 아예 안 움직인다

**원인** — Inspector 의 `Fall Speed` 가 `0` 이다. `3` 으로.

## 그래도 안 되면 — 답

> 실험까지 스스로 해봤다면 봐도 된다.

**순서 예시**

1. `fallSpeed` 를 `Update` 밖으로 빼고 `public` 을 붙인다 → Inspector 에 보인다
2. 값을 "1초에 갈 칸 수" 로 바꾼다 → `0.05 × 60 = 3`
3. 실제 움직일 거리는 `fallSpeed × Time.deltaTime` 으로 구한다

**완성 코드** — `Assets/Scripts/BirdMove.cs`

```csharp
using UnityEngine;

public class BirdMove : MonoBehaviour
{
    public float fallSpeed = 3f;

    void Update()
    {
        transform.position += new Vector3(0f, -fallSpeed * Time.deltaTime, 0f);
    }
}
```

**06번에서 뭐가 바뀌었나**

```diff
 public class BirdMove : MonoBehaviour
 {
+    public float fallSpeed = 3f;
+
     void Update()
     {
-        float fallSpeed = 0.05f;
-
-        transform.position += new Vector3(0f, -fallSpeed, 0f);
+        transform.position += new Vector3(0f, -fallSpeed * Time.deltaTime, 0f);
     }
 }
```

**`Time.deltaTime` 을 곱하는 이유**

`Time.deltaTime` 은 **이번 프레임이 걸린 시간**이다. 빠른 PC 는 작고 느린 PC 는 크다.

`fallSpeed` 를 **1초에 갈 거리**로 정해두고 여기에 곱하면,
**프레임이 짧으면 조금 가고 길면 많이 가서** 1초 뒤 위치가 언제나 같아진다.

곱하지 않으면 `fallSpeed` 는 **한 프레임에 갈 거리**가 되어, 빠른 PC 일수록 더 멀리 간다.

---

## 더 알고 싶으면

### 프레임 수가 4.5배 차이인데 왜 시간은 같나

실측값을 다시 보자.

| | 프레임 수 | 한 프레임당 이동 | 총 이동 |
|---|---|---|---|
| 60fps | 77장 | 3 × 0.024 = 0.071칸 | 77 × 0.071 = **5.5칸** |
| 10fps | 17장 | 3 × 0.113 = 0.340칸 | 17 × 0.340 = **5.8칸** |

**프레임 수가 줄어든 만큼 한 프레임의 이동 거리가 늘어난다.** 곱해보면 총 이동 거리가 같다.

이게 `Time.deltaTime` 이 하는 일의 전부다.

### 그럼 완전히 똑같아지나

**아니다. 0.086초 차이가 남았다.**

10fps 에서는 한 프레임에 0.34칸씩 뛴다. −5.5 를 정확히 밟지 못하고 **넘어가버린다.** 그 초과분이 오차로 남는다.

프레임이 적을수록 이 오차가 커진다. **그래서 "완전히 같다" 가 아니라 "0.3초 이내" 가 기준인 것이다.**

### 앞으로 계속 나온다

**움직임을 다루는 곳마다 `Time.deltaTime` 을 곱한다.**

- 11번 — 파이프가 흘러올 때
- 13번 — 몇 초마다 파이프를 만들 때 (시간을 **더할** 때도 쓴다)

13번에서는 곱하는 게 아니라 **더하는** 데 쓴다. 그때 다시 설명한다.

- **코드의 기본값을 고쳐보게 한다.** Inspector 값이 안 바뀌는 걸 겪어야
  "Inspector 가 코드보다 세다" 가 각인된다. 이후 항목에서 계속 발목을 잡는 함정이다
- **targetFrameRate 실험은 반드시 학생이 직접 두 번 돌리게 한다.** 표를 보여주고 끝내면
  이 항목의 핵심이 사라진다. 자기 Console 에서 숫자를 읽어야 믿는다

## 시연 절차
1. 06 코드에 deltaTime 만 곱해 Play → 너무 느려짐 → "단위가 바뀌었다" 를 유도
2. fallSpeed 를 3 으로 → 06 과 같은 속도 회복
3. Play 중 Inspector 에서 Fall Speed 를 1 / 10 으로 바꿔 실시간 반영을 보여준다
4. targetFrameRate 10 vs 60 을 나란히 돌리고 Console 시간을 칠판에 적어 비교

## 설명 게이트 ★
체크가 "deltaTime 을 곱하는 이유를 자기 말로 설명한다" 로 끝난다.
- 통과 기준: "프레임이 짧으면 조금, 길면 많이 움직여서 1초에 간 거리가 같아진다" 는
  **보상 관계**를 말하면 된다
- 부실한 답: "PC 마다 같게 하려고요" (결과만 말함) → "어떻게 같아지는데?" 로 되묻는다
- 두 번 부실하면 실측 표(프레임 수 × 프레임당 이동 = 총 이동)를 주고 직접 곱셈시킨다

## 분량
- 내가 걸린 시간: 코드 3분 + 검증 35분 (측정 방법 정정 포함)
- 학생 예상: 60~80분. **2부에서 가장 오래 걸리는 항목.** 개념이 어렵고 실험이 두 번이다
- 수업 배분 의견: **한 시간을 통째로 준다.** 여기를 대충 넘기면 10·13번에서 같은 벽을 또 만난다

## 검증 기록
| 체크 문장의 조건 | 결과 | 근거 |
|---|---|---|
| 코드를 열지 않고 Inspector 로 낙하 속도를 바꾼다 | O | SerializedObject 로 확인: "Fall Speed (fallSpeed) = 3" 노출됨 |
| targetFrameRate 10 과 60 의 시간 차이가 0.3초 이내 | O | **0.086초** (1.926 − 1.840) |
| deltaTime 을 곱하는 이유 설명 | - | 학생 확인 항목 |

검증 방법: Roslyn 으로 측정용 MonoBehaviour(HideFlags.HideAndDontSave)를 메모리에만
컴파일해 붙였다 뗌. y <= -5.5 를 넘는 순간의 Time.time / realtimeSinceStartup / frameCount 기록.

실측값:
- targetFrameRate 60 → 게임시간 1.840초 / 77프레임 / 평균 deltaTime 0.0239
- targetFrameRate 10 → 게임시간 1.926초 / 17프레임 / 평균 deltaTime 0.1133
- 차이 0.086초. 이론값 5.5 ÷ 3 = 1.833초와 둘 다 근접
- cp-06 대비: 곱하기 없을 때 1.653초 차이 → 곱한 뒤 0.086초 차이 (약 1/20)

## 제작 중 걸린 것 (교재에는 안 실음)
- 처음에 realtimeSinceStartup 으로 쟀더니 1.522초가 나와 이론값 1.833초와 안 맞았다.
  에디터에서는 Time.deltaTime 누적(Time.time)과 벽시계가 일치하지 않는다.
  게임 로직은 deltaTime 기준으로 움직이므로 **Time.time 으로 재는 게 맞다.**
  체크 문장의 "Console 에 찍힌 시간" 도 Time.time 을 가리킨다
- 학생 실험에서 이 문제는 안 생긴다. Time.time 을 찍게 하고 있기 때문
